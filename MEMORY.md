# chess-harness-codex — Repo Memory

## master-wisdom learner climb (out\lichess-master)
- `python tools\master_wisdom.py cycle --cycles 100` runs the depth ladder; viewer is `tools\live_pgn_viewer.py --port 8766 --pgn out\live\master-wisdom-live.pgn`. The learner engine is `engines\codex-chess-learner\codex-chess-learner.cmd` → `engines\codex-chess\codex_chess_uci.py` (an LLM, `masterWisdom.playModel` = gpt-5.5). State of record: `out\lichess-master\master-wisdom-state.json` (large, ~1MB — parse with python, don't Read whole). Each attempt = 10 games, pass at `passScore` 0.8; gate early-stops once the target is unreachable.
- The learner subprocess is spawned **fresh per attempt** by the ladder, so edits to `codex_chess_uci.py` **and** `chess-harness.config.json` values (re-read per move) are picked up on the next attempt — no cycle restart needed. BUT module-level constants in `tools\master_wisdom.py` (e.g. `MASTER_WISDOM_CLOCK_MS`) are baked into the running cycle process and **do require a cycle restart** to take effect. Never run two cycles at once (both write the same state.json); to restart, kill the `cycle --cycles` PID tree + any lingering `codex_chess_uci.py`, then relaunch via `Start-Process ... -WindowStyle Hidden -PassThru` with redirected logs. During the move-evidence scan / synthesis phase the cycle spawns several short-lived `master_wisdom.py`-matching PIDs (process-pool workers) that exit within seconds — don't mistake them for duplicate cycles; only the long-lived `cycle --cycles` PID is the real one.
- **Non-convergence gotcha (fixed 2026-06-14):** the climb sat at depth 1 for ~157 attempts, every one 0W/0D/3L "target unreachable", because the learner **forfeited every game on a timeout cascade**, not on the board (forfeit FENs were equal positions). Per-move budget is `clock/4` (cap `moveTimeoutSeconds` 45s); gpt-5.5 (~20-40s/move) drains its own clock while Stockfish answers instantly; on the first timeout the engine `await self.close()`s the app-server and retries with only `retryMoveTimeoutSeconds` 8s, but a cold app-server+thread restart alone takes ~8-10s, so all 3 retries time out → `bestmove 0000` forfeit, even with legal moves available ("the harness will not choose a move for you").
- **DO NOT add an engine "fallback" move** — the user explicitly rejected having the harness/engine pick a legal move for the learner ("no engine fallbacks"). A `fallback_best_move()` safety net was tried and **reverted**; the LLM must play every move itself.
- **Orphaned codex app-servers cause preflight timeouts (2026-06-15):** each learner attempt spawns an `@openai/codex` app-server (`node ... codex.js app-server` + `codex-win32-x64\vendor` child), and `codex_chess_uci.py close()` doesn't always reap them — they accumulate (~1 per attempt) and saturate resources, which makes the gpt-5.5 **play-model preflight** time out (was 45s+20 margin) and the cycle exit with `last_training_blocker = learner_model_preflight_failed`. Fix: before restarting, kill the orphaned npm-codex app-servers (match cmdline `app-server` + `@openai.codex`, EXCLUDE `WindowsApps` (the Codex Desktop GUI), `node_repl`/`cua_node`, and `modelcontextprotocol`/MCP), and raise `masterWisdom.playPreflightTimeoutSeconds` (set to 150). The blocker is infrastructure, not a ladder loss.
- **Accepted fix (2026-06-14): bigger clock + budget** so gpt-5.5 finishes full games on its own without timing out. `MASTER_WISDOM_CLOCK_MS` 600_000→1_800_000 (master_wisdom.py); `codex.moveTimeoutSeconds` 45→120 and `codex.retryMoveTimeoutSeconds` 8→60 (config — the bigger retry budget lets one slow move's retry survive the app-server cold restart instead of cascading to a forfeit). The clock change needed a cycle restart (see above). Tradeoff: full LLM games at 1800s take ~4-5 hrs per 10-game attempt → depth 1..8 is a multi-day, compute-bound climb. A learner timeout/forfeit is infrastructure, not a chess loss; the authored wisdom already covers "choose only from legal_moves", so convergence is a time-control issue, not a wisdom change.
